# 降智根因調查與修復報告

## 概述

用戶報告 CW 使用 vLLM 部署的 qwen3.6-35b-unc 模型時，在 goal 模式下出現「降智」：
第一輪正常（探索 + 修復），之後模型輸出碎片文字（「Done. Key improvements…」、
「Okay / No / Hmm」）且 agent 無限續跑，直到上下文爆量 / recursion error。
雲模型（deepseek / minimax）在同一 CW 環境下正常。

本報告記錄完整的調查、根因定位、修復與驗證過程。

## 一、調查過程

### 1.1 復現

用默認 data_dir 後端（`/Users/leon/Library/Application Support/Coworker`）、
ailicode workspace、qwen3.6-35b-unc 復現「修復1個bug」goal 任務：

- **修復前**：agent 迴圈跑了 **159 輪**，最終 `maximum recursion depth exceeded`，
  session 累積 162 條消息（最後 12 條是單詞碎片 `see / the / I / Security / audit…`）。
- 工具執行只有 **2 次**（第一輪的 read_file + replace_in_file），之後 107 輪全是純文字。

### 1.2 已排除的因素（逐項驗證）

| 因素 | 驗證方法 | 結果 |
|---|---|---|
| 採樣參數（temp/top_p/top_k） | vLLM `--enable-log-requests` 記錄每次請求 | ✅ 全部一致且正確（0.7/0.8/20/1.15） |
| 模型能力 | vLLM 直連 12-15 輪工具迴圈 | ✅ 完全正常 |
| stream / 非 stream | 兩者直連測試 | ✅ 都正常 |
| 工具集大小（3-26 個） | 多組測試 | ✅ 都正常 |
| 完整 system prompt（memory+skills+MCP+workspace） | vLLM 直連 | ✅ 正常 |
| 工具結果格式 | 真實 read_file 內容 | ✅ 正常 |
| vLLM 端錯誤 | docker logs | ✅ 無錯誤，全 200 |

**結論**：vLLM 端完全正常，降智只在 CW 的 goal 模式發生。

### 1.3 根因定位

通過 `llm-requests.log`（記錄請求 body）+ vLLM `--enable-log-requests`（記錄採樣參數）+
session 消息結構 三方對比，確鑿定位：

**根因：goal 續跑機制缺乏「本輪無實質進展」的停止條件。**

`main.py` 的 `_goal_rounds_iter`（goal 模式續跑循環）在
`goal.status == "active"` 時**無條件 `round_index += 1; continue`**：

```python
# ---- continue decision ----
goal = session_store.get_goal(session_id)
if goal is None:
    break
if goal.status == "active":
    round_index += 1
    continue   # ← 無限續跑！
...
```

**觸發鏈**：
1. 模型第一輪完成任務（或認為完成）後，輸出純文字碎片（無工具）
2. goal 仍為 active → agent **無條件續跑**下一輪
3. 模型每輪輸出碎片文字 → 無限循環（159 輪）
4. 上下文累積 → Summarizer 反覆觸發（43-112 次）→ 最終 recursion error

**為什麼雲模型正常**：雲模型（deepseek）在普通對話模式下測試（goal=null），
或輸出會觸發退化檢測/主動 update_goal。qwen 的碎片文字（「Done. Key improvements…」）
**不觸發** `is_degenerate_text`（該函數只檢測單條消息內的重複，而碎片是跨輪的不同文字）。

## 二、修復

### 2.1 修改 `backend/main.py`

新增輔助函數 `_goal_round_has_tool_execution(session)`：

```python
def _goal_round_has_tool_execution(session) -> bool:
    """Whether the latest assistant turn actually executed any tool."""
    try:
        if not session or not getattr(session, "messages", None):
            return False
        last = session.messages[-1]
        if getattr(last, "role", "") != "assistant":
            return False
        parts = getattr(last, "parts", None) or []
        return any(isinstance(p, dict) and p.get("type") == "tool" for p in parts)
    except Exception:
        return False
```

在 `_goal_rounds_iter` 的 continue decision 前加入空轉停止：

```python
# ---- 空转停止（防空转退化）----
if session_store.get_goal(session_id) is not None:
    try:
        _sess = session_store.require(session_id)
        if not _goal_round_has_tool_execution(_sess):
            break  # 本轮纯文字、无工具执行 → 视为完成/空转，停止续跑
    except Exception:
        logger.debug("idle-stop check failed", exc_info=True)
```

**邏輯**：每輪結束後，若模型**未執行任何實質工具**（parts 無 tool part），
即輸出純文字回答 → 視為任務完成或空轉 → 停止續跑。

**保護合法多輪任務**：每輪有 `replace_in_file` / `write_file` 等實質工具的輪
（parts 含 tool）→ 繼續續跑。「每輪修 1 個 bug」等多步任務不受影響。

### 2.2 新增測試 `backend/tests/test_goal_idle_stop.py`

6 個單元測試覆蓋：
- 純文字輪（空轉）→ 停止
- 工具輪（含 replace）→ 繼續
- 只讀研究輪（含 read_file）→ 繼續（有進展）
- 空 session → 停止
- 最後消息是 user → 停止
- 非 dict parts → 停止

## 四、根因總結

**降智的根本原因不是模型能力、不是採樣參數、不是 workspace 上下文，
而是 CW 的 goal 續跑機制在「模型已無實質動作」時仍然無限續跑。**

- qwen3 在任務完成（或自認為完成）後，輸出純文字碎片而無工具呼叫
- CW 的 goal 續跑無條件繼續 → 模型被迫每輪重複 → 碎片堆疊 → 上下文爆量 → 崩潰
- 雲模型因測試場景不同（普通對話）或輸出可被退化檢測捕獲，未暴露此缺陷

修復後：goal 續跑只在模型**實際執行了工具**（有實質進展）時繼續，
純文字回答即停止——既根治了空轉退化，又保留了合法的多輪任務能力。
